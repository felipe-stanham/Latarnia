# T-0025: A Machine Token cannot carry more than its owner's role

**Created:** 2026-11-25 | **Status:** [IN PROGRESS] | **Origin pitch:** none
**Branch:** `task-T-0025-token-scope-cap` | **Base:** `dev`
**Related:** [T-0023](T-0023.md) (per-App authorization). Found by the docs audit before promoting T-0023/T-0024 to tst
(code-suspect B3).

## Context

`POST /api/auth/tokens` (`create_token` in `src/latarnia/auth/routes.py`) accepts any `app_scope` from any logged-in
user. It only rejects role `full` for a non-superuser. It never checks the caller's own role on each App, so a user
with role `none` on App X can mint a `webUI-full` Machine Token for X. Every per-App check trusts the token's `apps`
claim (`GET /api/apps/{id}`, the UI API proxy since T-0023, API docs `_can_view`, the MCP Gateway), so that user then
reaches X's UI API, API docs and MCP tools with `webUI-full`. The docs (architecture.md, workflows.md) say token creation
needs a superuser session; the code and `test_non_superuser_cannot_mint_full_token` implement the narrower `full` rule.

## Goal

A non-superuser can mint a Machine Token only with, on each App, a role no higher than their own role on that App;
superusers are unchanged.

## Touches

- `src/latarnia/auth/routes.py` — `create_token`: for a non-superuser, reject (403) any `app_scope` entry whose role
  ranks above the caller's role on that App (`_role_for(actor, app_name)`, order = `ROLE_VALUES`). Keep the existing
  `full` rule and its message.
- `tests/integration/test_token_flow.py` — new cases (below).
- `docs/System/architecture.md`, `docs/System/workflows.md` — token creation rule (updated by `doc-updater` in step 6).
- **Pattern reference:** the existing `full` check in `create_token` and `test_non_superuser_cannot_mint_full_token`
  in `tests/integration/test_token_flow.py`.

## Tasks

- [ ] In `create_token`, after the role-value check, if the actor is not a superuser and
      `ROLE_VALUES.index(role) > ROLE_VALUES.index(_role_for(actor, app_name))`, raise 403
      `Cannot grant '<role>' on '<app_name>': your role there is '<own role>'`. Validate every entry before issuing; no
      token is created on any rejection.
- [ ] Integration tests for the acceptance criteria.

## Acceptance Criteria

- **t25-001:** Non-superuser with role `none` on `app_a` → `POST /api/auth/tokens` `{"label":"x","app_scope":{"app_a":"webUI-full"}}`
  → 403, body names `app_a` and `none`; `GET /api/auth/tokens` for that user lists no new token.
- **t25-002:** Non-superuser with role `webUI-med` on `app_a` → scope `{"app_a":"webUI-med"}` → 200 with a token;
  `{"app_a":"webUI-low"}` → 200; `{"app_a":"webUI-full"}` → 403.
- **t25-003:** Non-superuser with `webUI-med` on `app_a` and `none` on `app_b` → scope
  `{"app_a":"webUI-low","app_b":"webUI-low"}` → 403 and no token is created.
- **t25-004:** Non-superuser with role `full` on `app_a` (granted by a superuser) → scope `{"app_a":"full"}` → 403
  "Only a superuser can issue a token with the 'full' role" (existing rule kept).
- **t25-005:** Superuser → scope `{"app_a":"webUI-full","app_b":"full"}` → 200 (unchanged).
- **t25-006:** Non-superuser → scope `{"unknown_app":"webUI-low"}` → 403; scope `{}` → 200 (unchanged).
- **t25-007:** Existing `tests/integration/test_token_flow.py` tests pass unchanged; full suite green on ENV=dev:
  `PYTHONPATH=src .venv/bin/python -m pytest tests/ -q`.

## OUT of Scope / No-gos

- Do NOT change how tokens are validated or used (JWT checks, MCP Gateway, `_app_access_headers`).
- Do NOT revoke or cap existing tokens when a role is lowered later (separate follow-up).
- Do NOT change who may call `POST /api/auth/tokens` (any logged-in user stays allowed) or the token UI.
- Do NOT change the role model or `ROLE_VALUES`.
