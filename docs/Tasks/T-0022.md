# T-0022: Machine Token fixes — superuser 401 on `/api/apps/{id}`, same-second JWT collision

**Status:** [DONE]
**Branch:** `task-T-0022-machine-token-fixes`
**Created:** 2026-10-19
**Related:** [I-0002](../Pitches/I-0002.md) App REST API (relies on Machine Tokens, including one minted at every
App launch — both bugs must be fixed first). Found during the T-0020 regression run on dev.

## Context

Two Machine Token bugs:

1. **Superuser token gets 401 on `GET /api/apps/{app_id}`.** The same token gets 200 on `GET /api/apps`.
   `get_app` in `src/latarnia/main.py` only handles non-superuser JWT claims. A `super=true` claim falls into the
   session branch, finds no session user and returns "Authentication required". `list_apps` has the same branch
   shape and only works because `RoleStore.is_visible(None, …)` allows everything (the dev direct-access rule),
   not because it recognises the super claim. The integration test `test_token_scope_enforced` did not catch it:
   it tests a copy of the scoping rule, not `main.py`.
2. **Two identical mints in the same second collide.** `JWTAuth.issue` claims are `sub`, `iat` (seconds),
   `apps`, `super`, `exp`. Same inputs in the same second give byte-identical JWTs, so the `UNIQUE` constraint on
   `machine_tokens.token_hash` fails and `POST /api/auth/tokens` returns 500.

## Plan

- [x] `get_app`: when JWT claims are present, the token decides. A super claim gets access; a non-super claim
      needs a role other than `none` in its `apps` scope (else 403). The session branch runs only when there are
      no claims.
- [x] `list_apps`: same rule, explicitly. A super claim sees all Apps without going through `is_visible(None, …)`.
- [x] `list_apps`: re-raise `HTTPException` so its fail-closed 401 is not swallowed into a 500 (code review).
- [x] Audit the other claims/session branching sites: activity feed (`/api/activity`), `require_superuser`,
      `api_docs._can_view`, MCP Gateway `_role_for_app`/`_in_scope`. All already treat a super claim correctly; no
      change.
- [x] `JWTAuth.issue`: add a `jti` claim (random UUID4 hex) to every token, so every issued JWT and its hash are
      unique. Existing tokens (no `jti`) stay valid — nothing reads `jti`.
- [x] Unit tests: `get_app` and `list_apps` with super, scoped and out-of-scope claims; two same-second identical
      `issue` calls give distinct tokens and hashes; `create_token` twice with identical inputs inserts two
      distinct hashes.
- [x] `TESTS.md`: `test_dashboard_error_unmet_deps` names `buildStatusReasons` (renamed in T-0019).

Out of scope: `/api/auth/tokens` stays session-only (`_require_user` is cookie-only by design), so a Machine
Token cannot mint Machine Tokens. Per-App lifecycle endpoints under `/api/apps/{id}/…` are not touched.

Promotion triggers: one subsystem (auth), no schema change, no new service, one scope. Stays a Task.
