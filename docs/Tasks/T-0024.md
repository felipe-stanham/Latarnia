# T-0024: App names follow a safe pattern

**Created:** 2026-11-24 | **Status:** [IN PROGRESS] | **Origin pitch:** none
**Branch:** `task-T-0024-app-name-pattern` | **Base:** `dev`
**Related:** [T-0023](T-0023.md) (found in its code review, NIT-4).

## Context

A Manifest `name` only has a length limit (1–50). The platform interpolates it into the generated Caddyfile
(`handle_path /apps/{name}/*`, `header_up X-Latarnia-App {name}`), where Caddy expands `{…}` placeholders, and into
Postgres database/role names, systemd-facing log lines and API docs pages. A name such as `a{http.request.header.X}`
would let a client choose the App name `/auth/verify` checks; a name with `/`, spaces or upper case breaks or
aliases routes (Caddy path matching is case-insensitive). The operator installs Manifests, so the risk is low, but the
App name is a security-relevant identifier and should be one. Every real App (`latarnik`, `example_full_app`,
`example_companion`) and every test fixture already uses lowercase identifiers. `app-specification.md` still calls
`name` a "display name" with the example `"Camera Detection"`.

## Goal

The platform accepts an App only if its Manifest `name` matches `^[a-z][a-z0-9_-]{0,49}$`; an App with any other name
is not registered, and the operator sees why in the log.

## Touches

- `src/latarnia/managers/app_manager.py` — `AppManifest.name`: add the pattern (module constant `APP_NAME_PATTERN`).
  The existing `_parse_manifest` `ValidationError` path already logs `Invalid manifest in …` at ERROR and skips the App.
- `src/latarnia/web/api_docs.py` — comment only (~line 219): manifest names now have a pattern; keep the escaping as
  defence in depth.
- `tests/unit/` — a new test module for the name pattern and discovery (pattern reference below).
- `docs/System/app-specification.md` — Manifest `name` is an identifier with the pattern; examples use
  `camera_detection`. (Updated by `doc-updater` in step 6.)
- **Pattern reference:** the `public_routes` / `requires_secrets` validators on `AppConfig` and the `version` `pattern=`
  on `AppManifest` in `src/latarnia/managers/app_manager.py`; existing manifest tests in
  `tests/unit/test_app_manager.py` (or the closest existing manifest-parsing test module) for fixture style.

  51-character `a…a` → `ValidationError` on field `name`.
- **t24-003:** `AppManager.discover_apps()` over a temp `apps/` dir with two valid Apps and one whose Manifest name is
  `bad{x}` → the two valid Apps are registered, the bad one is not, and an ERROR log line contains `Invalid manifest`
  and the manifest path.
- **t24-004:** Every `latarnia.json` under `apps/` and `examples/` → parses with `AppManifest` without error.
- **t24-005:** Full suite green on ENV=dev: `PYTHONPATH=src .venv/bin/python -m pytest tests/ -q`.

## OUT of Scope / No-gos

- Do NOT add validation or skipping in `CaddyConfigManager` — the Manifest is the single validation point, and every
  registry entry is built from a validated `AppManifest`.
- Do NOT add a separate display-name field to the Manifest.
- Do NOT change `ManifestDependency.app`, App ids, Postgres name generation, or the `requires` lookup.
- Do NOT remove the escaping in `api_docs.py`.
- Do NOT rename any existing App.
