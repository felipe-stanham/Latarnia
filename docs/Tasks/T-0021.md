# T-0021: App API responses leak the App's Postgres password

**Status:** [DONE]
**Branch:** `task-T-0021-redact-db-credentials`
**Created:** 2026-10-19

## Context

The DB Provisioner builds `postgresql://{role}:{password}@{host}:{port}/{db}` for each App
with `database: true` and the App Manager stores it on the App Registry Entry as
`database_info.connection_url`, so the launchers can inject `DATABASE_URL` at start.
`DatabaseInfo.to_dict()` serializes every field, and every App endpoint returns
`AppRegistryEntry.to_dict()`:

- `GET /api/apps` (dashboard tiles; Machine Tokens scoped to the App)
- `GET /api/apps/{app_id}`
- `GET /api/apps/type/{app_type}`, `GET /api/apps/status/{status}`
- `POST /api/apps/{app_id}/prepare`

So any logged-in user who can see an App's tile, and any Machine Token scoped to it, can
read that App's DB credentials. Found during T-0020 regression on dev; pre-existing, and
prd (internet-facing behind Caddy) is affected.

The dashboard (`templates/dashboard.html`) reads only `provisioned`, `database_name`,
`role_name` and `applied_migrations` — never `connection_url`.

Logs were audited: `PgClient` logs role names only, `DbProvisioner` never formats the
password or URL, the Subprocess Launcher logs the command line with the `env:DATABASE_URL`
hint (not the value), and Secret Manager logs secret key names only. The only latent log
path is a dataclass `repr()` (which prints every field) ending up in a log line.

## Plan

- [x] `DatabaseInfo.to_dict()` drops `connection_url`. It is the single serializer behind
      every App endpoint, so one change covers all five. The field stays on the in-memory
      object — the Service Manager and Subprocess Launcher still read it to inject
      `DATABASE_URL`. Dropping beats masking: no consumer needs it, and `role_name` /
      `database_name` already carry the non-secret parts.
- [x] `connection_url` declared with `repr=False` on both `DatabaseInfo` and the DB
      Provisioner's `ProvisioningResult`, so a `repr()` in a log line or traceback can't
      print it.
- [x] Unit tests: the real `/api/apps`, `/api/apps/{app_id}`, `/api/apps/type/…` and
      `/api/apps/status/…` handlers in `latarnia.main` (registry patched with a provisioned
      App whose URL carries a known password) — payload JSON never contains the password,
      `connection_url` key absent, `database_name` / `role_name` / `applied_migrations`
      still present. `DatabaseInfo` / `ProvisioningResult` `repr()` omit the password.
      Provisioning a DB with logging at DEBUG (new role, existing role, role re-created
      from stored credentials) emits no record containing the password.
- [x] `TESTS.md` regression entry under Database.
- No dashboard change needed. No Manifest, schema or launcher change.

Promotion triggers: App Manager + DB Provisioner dataclasses only, one scope, no schema,
no new service. Stays a Task.

### Out of scope (noted, not fixed here)

- The systemd unit file the Service Manager writes carries `Environment=DATABASE_URL=…`
  (and `REDIS_PASSWORD` when set) and is created with the default umask, so it is readable
  by other local users on the host. Not an API or log leak; a separate hardening task
  (move it to the per-App `EnvironmentFile`, mode 600, like Secret Manager does).
- `GET /api/apps/type/{app_type}` and `GET /api/apps/status/{status}` apply no per-App
  role / Machine Token scoping, unlike `/api/apps`: any authenticated principal sees every
  App's registry entry. After this task they no longer expose the password, but the
  visibility gap remains — separate authz task.

## Acceptance

- **t21-001:** Registry holds an App with `database_info.connection_url =
  "postgresql://latarnia_crm_role:S3cr3t-pw@localhost:5432/latarnia_crm"`; call
  `GET /api/apps` as a Superuser → JSON contains no `S3cr3t-pw` and no `connection_url`
  key; the App's `database_info` still has `provisioned`, `database_name`, `role_name`,
  `applied_migrations`.
- **t21-002:** Same App, `GET /api/apps/{app_id}`, `GET /api/apps/type/service`,
  `GET /api/apps/status/running` → none contains `S3cr3t-pw`.
- **t21-003:** Same App, `GET /api/apps` with a Machine Token scoped to the App → App is
  listed, no `S3cr3t-pw`.
- **t21-004:** After `to_dict()`, the in-memory `DatabaseInfo.connection_url` is unchanged
  (launchers can still inject `DATABASE_URL`).
- **t21-005:** `repr()` of `DatabaseInfo` and `ProvisioningResult` carrying the URL → no
  `S3cr3t-pw`.
- **t21-006:** `DbProvisioner.provision_database("crm", …)` with logging at DEBUG (new role,
  existing role, role re-created from stored credentials) → no log record contains the
  password.
- **t21-007:** Unit suite green: `PYTHONPATH=src .venv/bin/python -m pytest tests/ -q`
  with `ENV=dev`.
- **t21-008 (post-merge):** Live dev platform restarted on `dev` after the merge:
  `GET /api/apps` → `example_full_app.database_info` has no `connection_url`, and the
  dashboard tile still shows the `DB (N migrations)` badge. Not a `[DONE]` gate: the local
  dev server on `:8000` runs from the main checkout, and a second platform instance from
  the worktree would rediscover the same Apps against the same Postgres.
