# T-0015: Dead app-count regression guard in both deploy workflows

**Status:** [ ]
**Branch:** _not created_
**Created:** 2026-09-08
**Filed by:** T-0013 (identified during T-0011, recorded in T-0012)

## Context

Both deploy workflows try to catch a deploy that silently loses Apps by comparing the App
count before and after. The guard has been inert since P-0008 made `/api/apps` require
authentication, and T-0012 recorded it as still visible in run 32372785880.

`deploy-tst.yml:33` and `deploy-prd.yml:44`:

```bash
PRE_COUNT=$(curl -sf --max-time 5 http://localhost:$PORT/api/apps | python3 -c "…['total_count']" 2>/dev/null || echo "-1")
```

`/api/apps` now answers 401, so `curl -sf` fails and `PRE_COUNT` is always `-1`. The check
itself (`deploy-tst.yml:88`, `deploy-prd.yml:99`) opens with:

```bash
if [ "$PRE_COUNT" != "-1" ] && [ "$POST_COUNT" -lt "$PRE_COUNT" ]; then
```

The first test is therefore always false and the comparison never runs. The deploy prints
`apps=-1` and reports "Deploy verified" regardless of how many Apps came back. A deploy that
dropped every App would pass this gate.

Worth noting the guard is not merely useless but misleading: the log line
`Deploy verified: health=good, apps=` reads like a successful verification.

## Scope (proposed — confirm before implementing)

Either make the guard real or delete it. Do not leave a third state.

- **Make it work.** Authenticate the call. P-0008 issues JWT machine tokens for exactly this
  kind of API access, so the workflow would need a token in repository secrets and the
  `Authorization` header added to both `curl` calls. Cost: a long-lived deploy token to
  manage and rotate.
- **Delete it.** Drop `PRE_COUNT`/`POST_COUNT` and the comparison, keeping the `/health`
  check that does work. Cheaper, and loses a signal that has not functioned since May
  anyway.

Recommendation when picked up: decide against whether an App-count drop is a failure mode
worth a deploy token. If not, delete — a guard that cannot fire is worse than no guard,
because its log line implies verification happened.

Both files must change together (`deploy-tst.yml` and `deploy-prd.yml`; prd is homeserver-only
since T-0018).

Promotion triggers to re-check when picked up: CI configuration only, no subsystem, no
schema, no new service — stays a Task.

## Acceptance Criteria (draft)

Depends on the branch chosen:

- **If made to work — ac-01:** A tst deploy logs a real integer for `apps=` (not `-1` and
  not empty).
- **If made to work — ac-02:** Forcing `POST_COUNT` below `PRE_COUNT` fails the job.
- **If deleted — ac-01:** `grep -c 'PRE_COUNT\|POST_COUNT' .github/workflows/*.yml` → 0.
- **If deleted — ac-02:** A tst deploy still fails when `/health` is not `good`.
- **Either way — ac-03:** No log line claims "Deploy verified" on the strength of a check
  that did not execute.
