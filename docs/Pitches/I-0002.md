# Pitch: App REST API

**ID:** I-0002
**Date:** 2026-10-18
**Status:** Ready for Promotion

---

## Problem

Latarnia is now a platform for exposing Apps, but an App can only be reached by a person in a browser (web UI, session cookie) or by an AI client through the MCP Gateway. There is no way for another App or an external system to call an App's API through the platform:

- `/apps/{name}/*` is gated by `forward_auth`, which only accepts a browser session. A Machine Token is rejected.
- Machine Tokens already carry a per-App scope and role, but they only work against the MCP Gateway and the platform API.
- The only API convention in the App spec is the UI API (`/api/{resource}`), which exists so the dashboard can render resources. It is read-only and not designed for machine consumers.
- `/docs` and `/openapi.json` of every App are served without authentication on an internet-facing host, publishing every App's API surface to anyone.

The first concrete consumer is **latarnik**. It scrapes documents and runs OCR. Several clients need to process those documents independently: sort them, assign them to cases, and so on. That logic lives outside latarnik, which stays common to every client. The intended chain is:

    latarnik (scrape + OCR)
      -> App-X (Latarnia App: categorizes documents per client definition)
           -> App-Multi-Tenant (outside Latarnia: per-tenant UI, its own end users)

Today none of these hops can go through Latarnia.

## Appetite

Medium: up to 2 weeks. The core is routing, token validation and identity forwarding on top of the existing auth model, plus platform-issued tokens for consuming Apps, the documented standard and fixture coverage. If it needs a new role model or a discovery service, it has outgrown this budget.

## Solution

Latarnia publishes each App's App REST API under a dedicated platform surface, alongside the web UI and MCP:

    /apps/{app}/...   web UI        browser session
    /mcp/...          MCP Gateway   Machine Token
    /rest/{app}/...   App REST API  Machine Token   (new)

- **Routing and auth by the platform.** A request to `/rest/{app}/...` must carry a Machine Token whose scope includes that App with a role other than `none`. The platform rejects anything else and forwards the request to the App's `/rest/...` routes with the same identity headers the web UI receives (user and per-App role). The App does no authentication. It only decides what each role may do, exactly as for the web UI.
- **Bearer only.** The App REST API does not accept a browser session. The web UI does not accept a Machine Token. The two surfaces stay separate.
- **App-to-App without manual tokens.** A consuming App declares, in its Manifest's `requires` entries, which Apps it calls and with which role. At launch, the platform issues a Machine Token for that App's App User, scoped exactly to those Apps and roles. It injects the token and the App REST API base URL into the App's environment, the same way it injects Secrets. Each launch gets a fresh token and the previous one is revoked. The called App sees the calling App as the user. The App never handles credentials or ports.
- **External consumers are platform users.** An external system (e.g. App-Multi-Tenant) uses a Machine Token issued manually by the superuser to a platform user, scoped to the Apps it may call.
- **Multi-tenancy is an App concern.** The tenant is data passed by the caller, not an identity. App-X trusts its caller and applies that client's definition. Latarnia knows nothing about tenants.
- **Documented standard.** The App spec defines the App REST API contract: the `/rest/` prefix inside the App, a required OpenAPI description, the error format and versioning. The current "REST API Endpoints" section is renamed to UI API.
- **App REST API docs.** Provided by T-0020, which ships first: the platform renders each App's App REST API docs at `/docs/apps/{app}/rest` behind the App's role. This pitch only needs the docs' "Try it out" to work against the new route.

## Boundaries

### IN Scope
- `/rest/{app}/...` route per Service App, accepting only a Machine Token scoped to that App with a role other than `none`, and forwarding identity and per-App role headers.
- Requests to `/rest/{app}/...` without a valid, in-scope, unrevoked token are rejected before reaching the App.
- `requires` entries may declare a role. For an App with such entries, the platform creates its App User, issues a Machine Token scoped to those Apps and roles at each launch (revoking the previous one), and injects the token and the App REST API base URL into its environment on both launchers (systemd and macOS dev).
- The App User and its tokens are removed when the App is deleted. When a `requires` role is removed or changed, the next launch's token reflects it.
- App REST API standard documented in `docs/System/app-specification.md`; UI API section renamed; "REST API ports" wording in `docs/SYSTEM.md` aligned.
- `example_full_app` exposes an App REST API and `example_companion` consumes it through an injected token, end to end.

### OUT of Scope
- **Direct App-to-App calls to an App's port.** Internal consumers go through `/rest/{app}/` with their injected token.
- **API docs (platform and App, UI API and App REST API), their gating and dashboard links.** Delivered by T-0020.
- **New roles for the API.** The existing role set is reused. No `api-read` / `api-write`.
- **Granting App-to-App access through the database or a UI.** The Manifest is the source of truth, under the same trust model as `requires_secrets`.
- **Multi-tenancy in the platform.** No tenant concept in Latarnia.
- **User self-service** (self sign-up, invitations, App admins managing users) and **richer user data for Apps** (email, display name). Separate pitch if needed.
- Rate limiting, quotas, usage metering, API keys distinct from Machine Tokens, a public API catalog.
- Streamlit Apps. They neither expose nor consume an App REST API.
- Changes to the UI API paths inside existing Apps.

### Cut List
1. Versioning rules in the standard (document the prefix and error format only).
2. Token rotation on every launch (issue once per App, revoke on delete).

## Risks & Rabbit Holes

- **Internal path to `/rest/`.** Calling the public hostname from the Pi hairpins through the router; a host-local entry point is a second ingress to secure. The injected base URL hides the choice from Apps, but it must still be made early. Do not build a discovery service.
- **Token lifecycle edge cases.** Rotation on launch must not break a running consumer that a systemd restart did not relaunch. Reconciliation of already-running units must not leave them with a revoked token.
- **Manifest self-granting.** Any App can declare access to any other App with any role. Acceptable only because installing an App is an operator action, the same trust as `requires_secrets`. Do not widen who can install Apps.
- **`requires` semantics change.** A missing dependency already blocks the dependent App. Adding a role must not change that behavior for existing entries without one.
- **Role wording.** `full` is documented as "webUI + REST API access", and the role names say `webUI-*`. The meaning must be restated for API callers without redesigning the role model.
- **Header trust.** Identity headers are trustworthy only because App ports are firewalled. That stays true, but any local process can still reach a port directly. Do not widen that.

## Open Questions

- Internal consumer path: through the public hostname, or a host-local entry point to the same route and auth?
- Expiry for manually issued Machine Tokens of external consumers, and whether a non-expiring token is acceptable.
- Does a forwarded request need to tell the App whether the caller is a person, an App User or an external consumer, or are user + role enough?
- Name and shape of the injected environment variables.

## No-Gos

- Do not let an App implement its own authentication for the App REST API.
- Do not accept a browser session on `/rest/`, or a Machine Token on the web UI.
- Do not let an App User log in or appear as a manageable person in user administration.
- Do not introduce a tenant concept in the platform.
- Do not build port discovery or any direct App-to-App channel.
- Do not change the role model.
