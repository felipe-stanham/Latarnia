# Memory

## Index

- **test-before-deploy:** Always run unit tests and local dev verification before deploying to TST. → [memory/testing-before-deploy.md](memory/testing-before-deploy.md)
- **log-deployments:** After every deployment, add a row to `DEPLOYMENTS.md` (date, target, branch, commit, notes). Do not skip.
- **claude-md-agnostic:** CLAUDE.md is a reusable template. Project-specific rules go in `docs/SYSTEM.md`, learnings go here.
- **example-apps-are-fixtures:** `examples/` is the source of truth for example apps (committed). `apps/` is gitignored. Platform changes must update `example_full_app` to exercise the new feature.
- **mcp-server-config:** MCP servers go in `.mcp.json`, not `settings.json`. User runs `claude-dor` profile. → [memory/mcp-server-config.md](memory/mcp-server-config.md)
- **scope-branch-naming:** Branch naming uses dashes not slashes: `scope-P-XXXX-N-description` (not `scope/`).
- **run-local-dev:** `cd /Users/felipestanham/Desktop/MyProjects/Latarnia && ENV=dev .venv/bin/python -m uvicorn latarnia.main:app --host 0.0.0.0 --port 8000 --app-dir src`
- **pi-remote-reverts:** The Pi's `/opt/latarnia/tst` git remote keeps reverting to an old repo name. Fix with: `ssh -i ~/.ssh/homeserver felipe@192.168.68.100 "cd /opt/latarnia/tst && git remote set-url origin https://github.com/felipe-stanham/Latarnia.git"`. Happens because rsync doesn't touch `.git/config`, so the stale remote survives deploys.
- **deploy-via-github-actions:** Deployment to `tst` and `prd` is handled by GitHub Actions, not manual SSH or the deployment-process skill. Push the branch and let the action run.
- **caddy-include-owner:** The per-env Caddy dir `/opt/latarnia/{env}/caddy/` and its `latarnia.caddyfile` must be owned by `felipe` (the service user), not root. Creating the placeholder with `sudo touch` leaves it root-owned and the platform fails Caddy config generation with `[Errno 13] Permission denied`. After creating it, `sudo chown -R felipe:felipe /opt/latarnia/{env}/caddy`.
- **runner-labels-not-arch:** Deploys select hosts by explicit self-hosted runner label (`homeserver`, `hetzner-latarnia-1`), never bare `runs-on: self-hosted` (non-deterministic with >1 runner) and never the default `ARM64`/`X64` labels. `prd` spans multiple hosts: one push to `main` fans out via a `fail-fast: false` matrix in `deploy-prd.yml` so instances can't drift. `workflow_dispatch` has a `host` input to catch up a host that was offline during a push. Adding a prd host = bootstrap it, register a labelled runner, add the label to the matrix.
- **deploy-needs-host-config-json:** `config/config.json` is gitignored (real config) with `config.example.json` tracked. The deploy Action runs `git reset --hard origin/main`, which DELETES a previously-tracked file but leaves host-local gitignored files alone. Each env root (`/opt/latarnia/{env}`) MUST have its own `config/config.json` (PG password, `{env}_latarnia_` prefixes, redis db, ports) created from the example BEFORE deploying, or the platform falls back to defaults → Postgres "no password supplied", env-root mis-resolves to `/opt/latarnia` (secrets.env + auth keys not found, Caddy written to wrong path), `/health`=error. Recover from the pre-deploy backup at `/opt/latarnia/backups/{env}/<ts>/config/config.json`. Bit prd on the first P-0008 deploy (2026-06-26).
- **deploy-backup-scope:** The deploy snapshot under `/opt/latarnia/backups/{env}/` exists only to recover host-local gitignored files `git reset --hard` cannot restore (`config/config.json`, `secrets.env`, `secrets/`, `caddy/`). It must never carry `data/`, `apps/` or `.venv/` — all gitignored, all untouched by reset, all reproducible; they took a snapshot from 5 MB to 1.5 GB. Retention is 2. Note `du -sh <dir>/*` hides dotfiles like `.venv` — use `du -sh <dir>` to size an env root. (T-0012)
- **stale-per-app-secret-files:** `{env}/secrets/{app}.env` is NOT cleaned up when a manifest stops declaring a secret — old keys keep being injected. Inverse of the P-0006 refuse-to-start gate, and it hides the opposite bug too: latarnik declares no `requires_secrets` at all while its code hard-requires `NOUS_API_KEY`/`ZAI_API_KEY` (`latarnik/main.py`), so on tst it crash-looped every 7s on a stale file holding only `ANTHROPIC_API_KEY` while prd survived on a hand-written correct one. When an App crash-loops on startup, check the per-app env file against both the manifest AND the app code, not just the master `secrets.env`. (T-0012 session note)
- **local-branch-is-dev:** The local checkout must always sit on `dev` — that is where the latest work lives and where we work. If a session finds it on `main`/`tst` (e.g. after a promotion), switch back with `git checkout dev` before doing anything else. Promotions to `tst`/`main` are merges done from `dev`, then return to `dev`.
- **tplinkdns-breaks-acme:** `home.stanham.com` is a CNAME → `stanham.tplinkdns.com` (TP-Link router DDNS). TP-Link's authoritative NS answer NXDOMAIN for AAAA of the host, for the zone's own NS/SOA and for `ns1.tplinkdns.com` itself. Strict resolvers (Google 8.8.8.8 from Europe, Let's Encrypt's) cache that and then fail the A lookup too, so Caddy's HTTP-01/TLS-ALPN renewals fail with `DNS problem: NXDOMAIN/SERVFAIL`. It expired the Pi cert on 2026-09-09 unnoticed; Caddy's storage cleaner then deleted the expired cert (2026-09-24) and renewal looped on "key not found" until a `systemctl restart caddy`. Checking from Uruguay (1.1.1.1/8.8.8.8) looks fine — test from Hetzner (`dig home.stanham.com @8.8.8.8`) instead. Fix is to stop depending on tplinkdns (A record / own DDNS at the stanham.com DNS provider).
